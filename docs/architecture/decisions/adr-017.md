# ADR-017: Observability and privacy

Version: 0.6 | Date: 21 October 2026 | Status: Partially Accepted

Owner: human owner/architect. Approver: human owner/architect; selective acceptance evidence below.

## Context

Distributed failures need correlation without leaking tank context or credentials.

## Options

Per-service uncorrelated logs; indiscriminate full payload capture.

## Original proposal (baseline subsequently accepted below)

OpenTelemetry, App Insights/Log Analytics and redacted diagnostics; audit separately.

## Consequences and verification

Sampling/retention/cost and safe operational fields need approval.

## Traceability

NFR-001–006, NFR-009. See [pack index](../../engineering/architecture-pack.md), [service design](../services.md) and [decision register](../../engineering/decision-register.md).

## Approval and history

0.1: initial proposal. No acceptance or supersession recorded. Human review must resolve outstanding details before implementation.

## Authorised refinement — 20 October 2026

Accepted: direct API/worker OpenTelemetry emission and propagated message trace context; no Service Bus queue solely for diagnostics. Numeric alert targets, retention, sampling and operational ownership remain proposed.

Evidence: [worker decision record](../../engineering/authorised-decisions-2026-10-20.md).

## Local/Development observability baseline — accepted 21 October 2026

OBS-01: instrument APIs and workers with OpenTelemetry; export Development diagnostics to shared Application Insights/Log Analytics. Correlate HTTP calls, outbox publication and message processing, retaining causation across retries. Use structured service/operation/outcome/duration/safe-error fields. Measure API failures/latency, dependency failures, outbox age, queue backlog, DLQ and worker failures. Local console diagnostics are the default; Azure export is explicitly configured. Never capture tokens, credentials, private notes, image content or complete request/response bodies in diagnostics. Business/security audit records remain separate from sampled diagnostics. Retention, sampling, alert thresholds and notification ownership remain unapproved details; this ADR remains Partially Accepted. [Approval](../../engineering/authorised-decisions-2026-10-21.md). No instrumentation/resources/configuration changed.

## Development diagnostic retention and sampling — accepted 21 October 2026

OBS-02: target 30-day diagnostic retention, subject to supported table settings and shared-platform approval; do not infer uniform retention or change shared settings without authorisation. Initially retain 100% of distributed traces while Development traffic is low. Application logs Information and above, suppressing routine health-check noise without hiding failures. Enable Debug/Trace temporarily for investigation and disable afterwards. Review telemetry volume and sampling before substantial load tests; introduce coordinated source sampling as volume grows, preserving trace consistency. Business/security audit retention is separate. Exact SDK/exporter settings, effective table retention and cost/access verification remain pending. [Approval](../../engineering/authorised-decisions-2026-10-21.md). Alerts/responders remain open; ADR remains Partially Accepted.

## Development alert ownership — accepted 21 October 2026

OBS-03: the human project owner is initial operational owner for Development. Send actionable alerts to an owner-designated email address (not yet selected/configured). Response is best effort during normal development hours; no overnight or 24/7 obligation or response-time SLA is established. Link alerts to affected services, diagnostics and recovery instructions without private payloads. Group repeated notifications and notify on recovery to limit noise. Reassess public-release support/escalation before Stage 4 launch. Exact thresholds, destination address and notification configuration remain pending; no message sending or resource changes authorised by this documentation task. [Approval](../../engineering/authorised-decisions-2026-10-21.md).

## Development alert thresholds — accepted 21 October 2026

OBS-04: initial Development investigation triggers, applied only as workloads become operational:

| Signal | Accepted Development trigger |
| --- | --- |
| API failures | HTTP 5xx rate >5% over 10 minutes with at least 20 requests |
| Low-traffic safeguard | At least 5 HTTP 5xx responses within 10 minutes, regardless of percentage |
| Unpublished outbox | Oldest pending record >5 minutes |
| Dead-letter messages | Any increase in DLQ count |
| Waiting commands | Oldest waiting command >10 minutes |
| Worker failures | At least 3 failed processing attempts within 10 minutes, including retries |

Exclude expected validation/access denials from unexpected API failure counts. Review thresholds after observing traffic. Successful processing drives applicable recovery notifications; DLQ alerts require investigation, not automatic replay. Latency, CPU/memory and dependency throttling are initially dashboard signals; alert settings follow agreed performance targets/measured shared-plan behaviour. These triggers are not availability guarantees. Exact evaluation cadence, signal scope/aggregation, recovery windows and implementation remain pending.
