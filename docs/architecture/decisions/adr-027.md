# ADR-027: Configuration, secrets and managed-identity access

Version: 0.4 | Date: 30 October 2026 | Status: Accepted; PP-owned exclusive instances and deferred deployment under ADR-031

Owner/approver: human owner/architect. Evidence: owner agreed configuration/secrets proposal and requested “Update docs on agreed above”.

## Decision

- Nonsecret deployed settings and feature flags: PP-owned service-isolated App Configuration stores, deployed when PP Bicep is altered (ADR-031).
- Unavoidable passwords/API keys/secrets: PP-owned service-isolated Key Vaults, deployed with the same PP Bicep work, not plain configuration values. App Configuration may store Key Vault references rather than secret values.
- Deployed APIs/workers use managed identities and least privilege wherever supported, avoiding stored credentials where possible.
- Local nonsecret defaults: version-controlled configuration files.
- Local development secrets: .NET User Secrets or equivalent untracked local settings; never source control. User Secrets is not encrypted and is not a production/trusted vault.
- No secrets in Angular's browser-delivered configuration, logs, images or build artefacts.
- Enforce application/workload access isolation; key prefixes and labels organise values but are not security boundaries. If shared services cannot enforce required access, obtain approval for suitable separate instances.

## Platform boundary and verification

Genuinely shared hosting/security remains platform-owned. PP owns the lifecycle, Bicep, security configuration, content and approved permissions of its exclusive configuration/vault instances. Verify authorised reads and denied cross-app reads, local setup without committed secrets, no browser/log leakage, and later agreed refresh/rotation/failure behaviour. Names/labels alone cannot establish access control.

## Accepted service-level access isolation

Approval evidence: the owner agreed least privilege per service and separate runtime versus deployment permissions, then requested “Update docs and list here which .md files contain the above information”.

- Aquarium API/worker identities may read only required Aquarium settings/secrets; Tracking and Advisor follow the same rule within their respective service.
- Each API/worker retains its own identity; service-level ownership does not imply identical permissions or shared credentials. Grant only the subset each workload needs.
- Nonsecret settings may be shared deliberately through explicit approved access; no automatic cross-service secret access.
- Deployment identity has approved configuration-management rights separately from runtime identities. Runtime cannot administer configuration/secrets; deployment access does not imply blanket read/administration of all secrets or the platform.
- Shared stores must demonstrably enforce required boundaries. Prefixes/labels alone are not security controls. If insufficient, propose suitably separate stores/vaults and obtain owner/platform approval rather than silently broadening access.

Exact role definitions/scopes, developer access assignments and naming remain unresolved; accepted developer identity and operational policies are recorded below. No permissions/resources/credentials changed.

Acceptance verification: required service reads succeed; cross-service config/secret reads are denied except explicitly shared nonsecret settings; runtime writes/administration are denied; deployment rights do not spill into other services/platform scopes.

## Accepted operational policies and local access

Owner agreed each proposal and requested this consolidated update.

- Load required configuration at startup; apply ordinary setting changes through controlled restart/redeployment in initial Development.
- Defer dynamic feature-flag refresh until a concrete feature needs it. A running job keeps its starting configuration; restarting workers must respect retry/idempotency and recover interrupted work.
- Prefer managed identities; rotate unavoidable secrets through documented operator-controlled process. With provider-supported overlap: create replacement, update Key Vault, restart affected apps/workers, verify, then revoke old credential. Without overlap use coordinated maintenance. Rotate promptly after suspected exposure.
- Updating Key Vault does not imply existing connections refresh. Automated scheduled rotation/provider-specific intervals remain later detailed design.
- Missing/invalid/inaccessible required settings/secrets at startup means not Ready and no protected requests/jobs processed; log safe diagnostics and use bounded retries.
- During a configuration-store outage, continue with already loaded settings only while required authorisation and downstream access still succeed. No hard-coded/production/broader-permission fallback.
- Recoverable worker failure retains work for retry rather than success acknowledgement; poison handling stays under the accepted retry/DLQ design.
- Developer Azure access uses individual Entra identities and scoped dev access (ADR-029); no shared accounts or copied workload credentials.

Concrete retry/timeouts, secret references/versions, provider overlap support and revocation mechanics remain implementation-readiness choices. No rotation, app restart, login or role assignment occurs in this documentation task.
