# ADR-012: Service-owned Function Apps on shared-plan hosting

Version: 0.2 | Date: 20 October 2026 | Status: Accepted

Owner/approver: human owner/architect. Evidence: [20 October approval record](../../engineering/authorised-decisions-2026-10-20.md).

## Context and alternatives

The project demonstrates large-system architecture with explicit operational tradeoffs despite modest expected traffic. Alternatives considered: a generic multi-store processor, queueing every write, direct write-then-publish, or independently hosted service workers.

## Decision

Use Aquarium Async Worker, Tracking Async Worker and Advisor Async Worker, one logical Function App per service. Initial photo processing is functions in Tracking's app, not a fourth worker. Worker functions handle local outbox publication and meaningful deferred work; APIs retain synchronous core CRUD. Use the existing shared-platform App Service Plan as the intended starting host, subject to compatibility/capacity/Always On verification.

## Consequences and verification

Each app has its own identity/deployment/configuration, not independent compute isolation on a shared plan. Verify OS/SKU/runtime, available CPU/memory/connections, concurrency and Always On before deployment. Image and AI work need bounded concurrency. Define extraction triggers from backlog/latency/contention; moving plans/scaling shared SKUs needs approval. Deploy Advisor only in its later stage.
