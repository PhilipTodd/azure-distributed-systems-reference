# ADR-016: Photo upload, limits and derivative lifecycle

Version: 0.3 | Date: 20 October 2026 | Status: Accepted

Owner/approver: human owner/architect. Approval evidence: [authorised decisions, 19 October 2026](../../engineering/authorised-decisions-2026-10-19.md), recording the owner's explicit chat directions and acceptance.

## Context

UI-only checks can be bypassed; direct Blob SAS does not enforce the application's maximum upload size. The owner approved uploading through Tracking and clarified exact bytes/crop/pad behaviour.

## Options

Direct-to-Blob plus post-upload rejection; API-proxied bounded upload. Only the latter enforces the chosen limit before saving an original to Blob.

## Decision

- UI checks the original file size and explains excess before upload.
- Upload binary through APIM to Tracking. Maximum file payload is 5,242,880 bytes inclusive.
- Tracking checks actual streamed bytes, not just headers. Reject excess with 413; use bounded temporary storage before Blob persistence and clean failures.
- No browser upload SAS, upload-intent route or separate browser success/completion call. Tracking records successful storage and durable processing work, then returns 202/status Location.
- A Tracking-owned worker validates/scans/decodes the original and creates two WebP derivatives: cropped 400 x 400 thumbnail and padded 1200 x 800 hero.
- Retain original for future processing; strip metadata from derivatives. Mark Ready only when both derivatives/metadata are durable.
- Future gallery displays thumbnails; click opens hero. Gallery release timing is not accepted here.
- No photo content is supplied to AI.

## Consequences and verification

API/edge handle binary traffic; managed identity writes private Blob storage. Multipart/request limits must allow only bounded overhead above file limit. Rate/concurrency/decode resource controls require specification. Blob/metadata/work publication is not atomic: use idempotency, cleanup and reconciliation.

Test max-1/max/max+1 bytes, misleading/absent length, interrupted request, authorisation, invalid content, orientation, derivative dimensions/crop/pad, retries, orphan cleanup and private original retention. No oversized original is accepted.

WebP quality, alignment, padding colour, upscaling, source formats, decoded pixel cap and retention duration remain TBD.
