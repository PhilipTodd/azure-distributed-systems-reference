# ADR-006: History without full event sourcing

Version: 0.3 | Date: 26 October 2026 | Status: Accepted

Owner: human owner/architect. Approver: human project owner. Approved: 26 October 2026. Evidence: [approval record](../../engineering/authorised-decisions-2026-10-26.md).

## Context and options

The label Parameter Event Store does not establish event sourcing. Full event sourcing and current state without revision history were considered. Measurement corrections need traceability without rebuilding current state from events.

## Decision and scope

Use current records plus immutable revision/audit history. Do not implement full event sourcing. This policy applies initially to parameter measurements only; maintenance, observations, photos and internal processing records require separate lifecycle decisions.

## Measurement identity and versions

Each version has a unique record ID; all versions of one measurement share a stable measurement ID. Parameter definition identity is separate. Link versions using `supersedesRecordId` and `supersededByRecordId` where applicable.

Keep measurement time separate from server-recorded version creation and operation times. A correction retains measurement time unless the user explicitly corrects it.

## Operations

- Insert: create an `Active` version with a `Created` entry in its JSON `History` list.
- Update: atomically create a new `Active` version and mark the previous active version `Superseded`. Record the supersession on the previous version, linking the replacement; the replacement has its own creation entry and links its predecessor.
- Delete: mark the current active version `Deleted` and append a `Deleted` entry. Earlier versions remain `Superseded`; deletion never reactivates them.
- Restore: while history is retained, create a new `Active` version from the deleted version, link it into the version chain and record restoration and creation. Preserve the earlier deletion and its history.

Each measurement has at most one active version. Ordinary charts, reports, trends and subsequent calculations use only `Active` versions. Audit views can follow the complete chain. Previously generated advice preserves the exact version IDs and input values used; correction does not rewrite past advice. Future advice uses corrected current values.

A correction to one or several readings must validate the resulting measurement panel before committing changes. Exact physical representation of reading versions within the existing panel model remains implementation-readiness work.

## Structured audit history

Each History entry contains `operation` (`Created`, `Superseded`, `Deleted` or `Restored`), server-generated UTC `occurredAt`, authenticated `actorId`, `operationId`, and `relatedRecordId` where applicable. A user-entered `reason` is optional. Generate readable messages from these fields rather than storing prose as the audit structure.

Obtain actor identity from the authenticated context, not an untrusted user-supplied ID. Existing History entries cannot be edited or removed through normal application operations. Status and history-list changes make the enclosing records mutable; existing audit entries remain immutable.

## Consistency, concurrency and retries

Changes identify the version the user last read. Replacement, supersession, related history changes and the applicable local outbox commit atomically within the accepted Tracking transaction boundary (ADR-005/007).

Reject stale edits and edit/delete races: the first successful operation wins, and the other receives a conflict. Show: "This measurement has changed. Reload it before saving." Preserve entered values for comparison. Do not silently overwrite changes or create multiple active versions.

Use `operationId` to recognise retries and return the existing result instead of repeating the operation. Exact executable concurrency and idempotency contracts remain to be specified and verified.

## Retention and permanent erasure

Initially retain all measurement versions and History without automatic expiry. Review this explicit initial policy before production use. Normal deletion is logical and retains the version chain.

Permanent erasure is a separate controlled operation covering the complete version chain and associated history. Its permissions and treatment of dependent advice snapshots must be decided before implementation of that operation. Actor-identity retention and broader privacy/account-deletion integration remain part of this readiness work; this policy does not override required erasure.

## Consequences and verification

Current queries do not replay events, but version chains and audit lists grow over time. Validate storage growth, indexing and transaction feasibility against the existing panel model before implementation; no new store or service boundary is authorised.

Verify atomic failure behaviour, concurrent corrections, edit/delete races, retry deduplication, timestamp corrections, panel validation, active-only views, unchanged historical advice inputs, restoration and protection of existing audit entries. These are required future checks, not completed tests.
