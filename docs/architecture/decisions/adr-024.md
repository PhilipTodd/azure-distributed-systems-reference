# ADR-024: Shared platform ownership, Aquarium schema and Tracking containers

Version: 0.2 | Date: 20 October 2026 | Status: Accepted

Owner/approver: human owner/architect. Evidence: acceptance of the platform/application ownership split, use of Aquarium schema, and “I agree with above recommendations regarding Cosmos container ownership and Aquarium DB schema. Update docs”.

## Evidence and alternatives

Inspected C:\Git\azure-reference-platform: docs/resource-ownership.md, docs/deployment-settings.md, infra/bicep/main.bicep and environments/dev/main.dev.bicepparam. These define intended development resources, not verified deployment.

Alternatives: app-managed dedicated SQL/Cosmos databases or more physical isolation. Selected shared hosting matches low-cost development goals while preserving logical ownership.

## Decision

- Platform repository owns shared App Service Plan/capacity, SQL logical server and ReferenceProjectsDb, Cosmos account and ReferenceProjects database/throughput, Service Bus namespace, and shared monitoring/network/platform-wide policies.
- Parameter Pilot owns app resources: APIs/Function Apps/frontend/gateway where application-specific, identities and approved access assignments, SQL Aquarium schema/tables/migrations, Tracking containers/indexes/data lifecycle, Service Bus queues/topics/subscriptions and application configuration.
- Accepted target shared hosting includes APIM, ACR, Key Vault, App Configuration, Blob Storage account and PostgreSQL Flexible Server. Owner will separately request platform Bicep/deployment outside Parameter Pilot's agentic process; verify resources before application implementation. Earlier inspection did not establish these resources.
- Aquarium uses [Aquarium] schema within platform-owned ReferenceProjectsDb, not a new application-owned SQL database. Domain tables plus Outbox/Inbox and app EF migration history must be scoped to that schema.
- Aquarium API and worker runtime identities receive only needed rights within Aquarium schema, no broad access to other applications' schemas. Migration rights are separate and narrowly controlled; do not grant runtime database-owner privileges.
- Tracking owns its containers inside platform-owned ReferenceProjects Cosmos database. Restrict Tracking API/worker data-plane permissions to its containers; other services use Tracking APIs.
- App deployment may create/manage approved child resources at delegated scopes but may not change shared database throughput, plan/namespace SKUs, platform-wide policies or other projects' resources. Platform owners approve capacity changes.

## Consequences and verification

Database/compute/broker contention and shared recovery blast radius remain. Schema/container access is logical isolation, not independent physical capacity or per-app restore. Test permissions, migrations, transactions and shared backup/restore reconciliation before production.

Referenced platform docs describe application Cosmos databases while Bicep already creates a shared database. For Parameter Pilot, the accepted choice is container ownership within that shared database. No platform repository change is authorised in this task.

Exact roles, container names/count, indexes, deployment permissions and live inventory remain TBD. /tankId is accepted separately in ADR-005. Accepted refinement: platform owns PostgreSQL server/capacity/extensions/backups; Advisor owns its database/tables/migrations/data. Platform additions are not yet verified.

## Extended platform ownership and process

The owner agreed shared APIM/ACR/Key Vault/App Configuration/Blob/PostgreSQL hosting. Application ownership remains API routes/policies, images, secrets/configuration, private photo containers/lifecycle and Advisor database/data. Verify enforceable Key Vault/configuration isolation; prefixes/labels do not grant boundaries. Platform work is externally managed and separately requested; app agents do not perform it. Initial hosting is dev only (ADR-025); no Test/Production provisioning yet.
