# ADR-009: Entra External ID, token validation and per-tank authorisation

Version: 0.12 | Date: 21 October 2026 | Status: Accepted

Owner/approver: human owner/architect. Evidence: the owner accepted the six-point identity/authorisation proposal with “I agree. Update pack.” See [approval record](../../engineering/authorised-decisions-2026-10-20.md).

## Context and options

Authentication at the gateway does not prove tank ownership or permit a worker to operate on arbitrary user data. Alternatives were another identity provider or authorisation based only on browser/gateway context; neither is selected.

## Decision

1. Angular uses Microsoft Entra External ID authorisation-code flow with PKCE to sign in and obtain an API access token.
2. UI sends an API access token through APIM; APIM validates applicable issuer, audience, signature, lifetime and required permissions.
3. Every receiving API independently validates applicable access tokens/permissions. Gateway validation is not a substitute, and an ID token is not an API access token.
4. Aquarium maps a validated stable identity to an internal user ID and owns tank-access decisions. Email and browser-supplied user IDs never establish ownership.
5. Tracking requests authorised tank access from Aquarium, including the accepted once-per-panel parameter-validation batch (ADR-023). Each protected operation enforces resource access; inaccessible resources are not disclosed.
6. Workers use managed identities/least privilege for workload access and retain trusted originating actor/tank context where required. Workload authentication does not confer arbitrary owner access.
7. If required authorisation information cannot be obtained or validated, fail closed; do not return protected data, perform protected work or save a new panel/outbox merely to mask dependency failure.

## Workload and actor context

Customer access tokens and managed-identity workload tokens have distinct purposes. Define allowed issuers/audiences, delegated scopes versus app permissions, and trusted actor propagation per route. A client-supplied header or body actor ID is not proof. Validate resource access at processing/result retrieval as required.

Do not persist bearer tokens in outbox/queue messages or telemetry as a substitute for durable actor references. Exact delegation/token exchange/assertion mechanism remains design-readiness work; fail closed until it is defined, rather than trusting unsigned context.

## Still open

External ID tenant/app registrations, concrete scopes/roles/claims, workload issuer configuration, future provider/account-linking policy, detailed conditional policies (customer MFA sequencing accepted below), exact local developer role/credential-selection configuration, exact session durations/policy and detailed delegation/revocation/timeout rules remain TBD; client storage/renewal is accepted below. No tenant configuration, identity provisioning or platform role changes are authorised by this documentation task.

## Verification and consequences

Test missing/expired/wrong-issuer/wrong-audience/bad-signature or insufficient-permission tokens at APIM and APIs, direct API bypass attempts, forged owner IDs, cross-tank requests, expired/revoked actor access during async work, and Aquarium outage. Demonstrate internal identity stability across email changes and no tokens/private claims in telemetry.

Fail-closed owner API dependencies trade availability for isolation. Synthetic dev identities remain separate from eventual production under ADR-025.

## Customer sign-in and account isolation — accepted 21 October 2026

Authority: [ID-06–08 approval record](../../engineering/authorised-decisions-2026-10-21.md).

Use a dedicated External ID customer tenant and its tenant-specific ciamlogin.com authority with local email one-time-passcode sign-up/sign-in initially. Social/federated sign-on is deferred to a later stage requiring separate approval. Customer registration does not use workforce B2B guest invitations.

A customer account may use the same email address as an existing personal Microsoft account. Do not infer identity equivalence from that address. Resolve a validated stable tenant/issuer-qualified identity to Aquarium's internal user, never automatically link accounts or grant tank access by email alone.

Existing Microsoft-account cookies do not by themselves authenticate the separate local customer account. Domain/session separation supports the design, but strict issuer/audience/signature/lifetime/permission validation at APIM and each API is required. Configure the specific customer authority rather than a common/consumer authority. Do not enable Microsoft-account federation as an implicit fallback.

Show the active customer account and provide sign-out/switch-account. A pre-existing customer session may provide normal SSO; a new passcode is not guaranteed on every application visit. Email delivery/mailbox access is a dependency, and email passcode alone is not MFA.

Verify in one browser profile while already signed into a personal Microsoft account using the same email: customer registration/login succeeds as the correct customer identity; sign-out and account switching behave correctly; unrelated Microsoft tokens are rejected; identities/tanks never merge because emails match. Do not make signing out of Microsoft or separate browser profiles a normal product prerequisite.

References: [customer authentication methods](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-authentication-methods-customers), [authentication domains and sessions](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-custom-url-domain). Actual tenant/session configuration and verification remain pending.

## Customer session handling — accepted 21 October 2026

ID-10: use MSAL Angular with its supported localStorage cache configuration. Tabs on the same application origin can share the cache and it can persist across browser restarts. Use supported compatible pinned MSAL versions; do not build a custom token cache or assume cached tokens remain valid indefinitely.

Acquire/renew tokens silently where possible; request interactive sign-in when required. Application cache and External ID session cookies are separate: cache persistence does not guarantee continued sign-in, and clearing cache does not itself end the identity-provider session. Exact tenant session settings remain to verify.

Sign-out clears application authentication state via supported MSAL handling and initiates External ID sign-out. Coordinate UI state across tabs; verify sign-out/account changes in other open tabs and prevent stale private data being shown under a new account. Sign-out does not guarantee immediate invalidation of already-issued access tokens.

Retain unsaved measurement input in memory while the same user reauthenticates; clear it if a different account signs in or the user explicitly signs out. Do not persist unsaved private measurement drafts in localStorage as a consequence of selecting the authentication cache. Browser refresh/navigation can lose an in-memory draft.

Show the active account and provide sign-out/switch-account. Explain shared-device implications where useful. Protect against XSS and dependency compromise; localStorage is accessible to application JavaScript and is not a secret vault. Verify refresh, multiple tabs, browser restart, expired/rejected tokens, interactive fallback, sign-out and identity changes with controlled accounts. No specific idle timeout, absolute session duration or tenant persistent-session policy is selected here.

Evidence: [ID-10 approval](../../engineering/authorised-decisions-2026-10-21.md). Reference: [MSAL cache guidance](https://learn.microsoft.com/en-us/entra/msal/javascript/browser/caching). No authentication code/settings changed.

## Customer API permission boundaries — accepted 21 October 2026

ID-11: separate delegated customer read/write permissions per service. Proposed scope names are Aquarium.Read/Aquarium.Write and Tracking.Read/Tracking.Write; exact scope URIs/names and registration configuration remain to validate. Define Advisor permissions during Stage 5 requirements.

APIM and each receiving API enforce the permission applicable to the operation. A delegated API permission allows the application to act on behalf of the authenticated user; it never grants ownership of all tanks. Independently enforce Aquarium-authoritative per-tank access. Missing permission or failed ownership checks deny the operation. Do not infer that Write includes Read without an explicit route policy.

Customer delegated scopes and workload application permissions are distinct; no worker gets customer authority merely by having a managed identity. Exact API audiences, app registrations/consent, route-to-scope mapping and service-to-service delegation remain readiness work. Verify wrong-service tokens, insufficient scopes, read-only mutation denial and cross-owner requests. [Approval ID-11](../../engineering/authorised-decisions-2026-10-21.md). No registrations/grants changed.

## Synchronous delegated API calls — accepted 21 October 2026

ID-12: use OAuth On-Behalf-Of (OBO) for synchronous customer-authorised calls between APIs. Tracking validates its incoming delegated access token, then uses supported MSAL/Microsoft identity integration to obtain an Aquarium-audience delegated token with the required downstream permission. Aquarium validates that token, its authorised calling application/delegation and per-tank ownership. Do not forward a Tracking-audience token as an Aquarium credential or treat a caller-supplied actor ID as proof.

Apply this approach to applicable synchronous customer request chains; exact scope names, app registrations/consent, confidential-client authentication, caller restrictions and External ID configuration must be validated before implementation. Prefer supported managed identity/federation where compatible for client authentication; this acceptance does not select a credential mechanism or grant permissions. No silent fallback to unsigned actor context if OBO fails. Fail closed and preserve UI input for retry without panel/outbox persistence.

OBO is not the worker authorisation mechanism. Async workers use managed identities and durable trusted actor context; no customer bearer tokens are stored in outboxes/messages/logs. Worker context/delegation remains a separate decision.

Verify downstream identity mapping/ownership, wrong audience, missing delegated scope, unapproved caller, token-exchange failure and dependency outage. [ID-12 approval](../../engineering/authorised-decisions-2026-10-21.md). References: [OBO protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow), [External ID flow support](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-supported-features-customers). No registrations/code/settings changed.

## Durable worker authorisation context — accepted 21 October 2026

ID-13: server-owned job records are authoritative for protected asynchronous work. The accepting API authenticates the customer, checks tank access and saves internal user ID, tank ID, operation and relevant immutable input snapshot with the job and local transactional outbox. The command references the job; its fields alone do not grant access.

The owning worker authenticates with its managed identity, loads the authoritative job only from its service-owned store and checks consistency of job/command context. Restrict permitted command senders; reject inconsistent or unauthorised references. No customer bearer tokens in jobs, messages, outboxes or diagnostics. This is distinct from synchronous OBO.

Before protected processing, obtain current access and applicable entitlement decisions through Aquarium using an explicitly authorised workload contract. If Aquarium is temporarily unavailable, leave work recoverable with bounded retry. If access is revoked, stop protected processing; do not release protected results. Result retrieval independently checks access. A persisted user/tank reference is provenance, not proof of current ownership.

Outbox publication of an already-committed measurement fact can proceed without a new customer authorisation check; it does not authorise fresh protected work. Separate audit/event publication from new user-sensitive processing. Exact workload permissions, internal check contracts, status/error/retry settings and long-running recheck boundaries remain to specify.

Evidence: [ID-13 approval](../../engineering/authorised-decisions-2026-10-21.md). No application, permissions or resources changed.

## Internal workload API boundary — accepted 21 October 2026

ID-14: dedicated internal worker operations require approved workload identity, operation-specific permission and actor/tank/action validation. Customer operations require delegated customer tokens. A managed identity alone never grants all-tank access. Aquarium provides current actor/tank access and applicable-entitlement checks; Tracking provides authorised history retrieval for Advisor at Stage 5. Exact contracts, audiences, allowed callers and permissions remain to specify before implementation. Preserve network restrictions and independent token validation. API-025 remains synchronous OBO despite its /internal URL; route naming alone does not determine token policy. ID-13 authoritative job context is required, not arbitrary browser actor fields. Verify unapproved callers, missing permissions, forged context and customer/workload token substitution are denied. [ID-14 approval](../../engineering/authorised-decisions-2026-10-21.md). No grants, code or topology changed.

## Stage 2 identity configuration — accepted 21 October 2026

ID-15: approve three registrations in the dedicated customer tenant: Parameter Pilot UI, Aquarium API and Tracking API. Each API validates its own audience. Confirm delegated scope names Aquarium.Read, Aquarium.Write, Tracking.Read and Tracking.Write; full scope URIs/registration GUIDs remain actual setup outputs. Aquarium uniquely maps validated tenant ID plus object ID (tid + oid) to internal user ID; do not use email or application-specific sub for cross-API identity matching. Verify required claims and reject missing/untrusted identity context.

Only the approved Tracking application may use OBO for Aquarium panel validation, requiring Aquarium.Read and independent tank ownership. Route policies must also restrict the calling application; a scope alone does not approve all callers. Tracking authenticates as a confidential client using a registered certificate. Protect Development private key in Key Vault; local Tracking uses a separate local certificate outside source control. Select/verify secure supported library loading, private-key permissions, credential rotation and registration of both public certificates; no private key is shipped to the UI. Certificate authentication supplements, rather than replaces, the delegated OBO token.

Register explicit localhost redirect addresses for authorised Local development and explicit Development redirects; no invented/wildcard deployment addresses. Advisor registrations remain deferred. Exact GUIDs/audiences/URIs/redirects/certificate references and supported implementation are setup/verification tasks, not new product choices. No registrations, certificates, grants or settings were created.
