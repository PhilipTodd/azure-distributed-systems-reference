# ADR-031: PP-owned service-isolated configuration and vault instances

Date: 30 October 2026 | Status: Accepted ownership/isolation direction; deployment deferred

Owner/approver: human owner/architect. The prior platform-managed-instance proposal was not accepted and is superseded here.

## Approval evidence

After challenging platform ownership of resources exclusive to PP, the owner agreed with PP ownership and stated: "Agreed. We will deploy the App Config and Key Vaults when we alter the PP repository bicep files. Update the documentation and proceed with the next item."

## Decision

- PP owns lifecycle, Bicep, security configuration, content and approved permissions of App Configuration stores and Key Vaults used exclusively by its services. They do not belong in the shared-platform repository.
- Retain the initial service-isolated arrangement for Aquarium and Tracking: one Free App Configuration store and one Standard Key Vault per service. Later Advisor resources wait for its stage. Review exact names/settings/grants with PP Bicep; this document creates none.
- Provision through PP's existing infrastructure/deployment path when PP Bicep is altered. Do not add these instances to azure-reference-platform/main.bicep or require that repository to provision them before PP infrastructure preparation.
- Each runtime keeps a distinct managed identity and only required configuration/secret access. Runtime, deployment and administration permissions remain separate. Labels/prefixes are not security boundaries. Existing startup/rotation/failure policies remain accepted.
- Genuinely shared plan, APIM, ACR, SQL server/database, Cosmos account/database, Service Bus, monitoring and later PostgreSQL server remain platform-owned. Advisor owns its later database/content.

## Consequences and verification

Lifecycle ownership now follows exclusive use. Quotas, scoped grants, safe secret handling and operational behaviour still need verification. Free-tier/store and Standard-vault usage assumptions remain subject to actual supported settings and accepted budget; no automatic paid upgrade or new spend is approved. Deployment sequencing deferral does not waive final Stage 1 access/readiness evidence.

Before readiness, verify required reads, denied cross-service reads, denied runtime writes/administration and bounded deployment management. Provisioning, secret creation, exact privilege grants and deployment verification remain separate work.

## Affected architecture and records

Refines ADR-024/027; retain ADR-009 identity and ADR-026 ingress. Existing Structurizr workspace/systems/relationships/deployment sources were consulted. PP and shared-platform deployment descriptions now reflect this ownership; configuration/vault infrastructure remains omitted from logical views. No new domain service, data flow, duplicate C4 diagram or resource was created.
