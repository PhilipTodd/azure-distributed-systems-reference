# ADR-026: Development API ingress through APIM with restricted public backends

Version: 0.1 | Date: 20 October 2026 | Status: Accepted approach; addressing feasibility unverified

Owner/approver: human owner/architect. Evidence: owner accepted APIM gateway arrangement and then “restricted public endpoints for Development, subject to verifying APIM and workload addressing”.

## Decision

Browser API requests use the shared APIM HTTPS endpoint. Backends remain publicly addressable HTTPS endpoints but deny unapproved source traffic through App Service access restrictions. Permit verified APIM outbound addresses and required API/worker source addresses; deny other inbound sources.

Independent token validation and resource authorisation remain mandatory under ADR-009. Source-address permission does not prove service or user identity. CORS, hostnames or browser headers are not substitutes for an enforceable restriction.

Defer Front Door/WAF until release preparation. Private backend networking remains an alternative to reassess, not the selected initial Development mechanism.

## Mandatory feasibility gate

Confirm the platform APIM tier/address behaviour and permitted workloads' complete effective outbound address sets support sufficiently narrow, reliable rules. Do not broadly allow an Azure region merely to accommodate shared outbound addresses. Shared plan addresses may identify several workloads; token/role checks still enforce logical identity.

If sufficiently narrow reliable access cannot be established, revisit mechanism/tier/private-network alternatives with the owner before implementation; never silently deploy open backends. Exact rules, IP-change handling, SCM/deployment/probe access and operational exceptions remain detailed work requiring verification.

## Verification

Show APIM requests succeed, arbitrary internet/direct browser API requests are denied even with otherwise valid user token, approved internal callers authenticate and perform only permitted actions, unrelated callers sharing allowed network origin still fail token/role checks, and invalid tokens are rejected through APIM and APIs.

Do not configure restrictions until platform facts/permissions are verified. This is not a claim of private networking or current protection.
