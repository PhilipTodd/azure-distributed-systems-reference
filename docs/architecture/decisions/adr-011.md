# ADR-011: Separate containerised API apps on shared Development hosting

Version: 0.2 | Date: 20 October 2026 | Status: Accepted

Owner/approver: human owner/architect. Evidence: owner agreement to the Development API hosting proposal, now instructed to update docs. See [approval record](../../engineering/authorised-decisions-2026-10-20.md).

## Decision

Development uses three separate containerised App Service API apps: Aquarium, Tracking and later Advisor. They target the existing shared Linux App Service Plan, alongside the three service-owned worker Function Apps accepted in ADR-012. Each app has its own managed identity, deployment and configuration.

Deploy Advisor only in its later stage. Keep workload concurrency bounded and monitor shared CPU, memory and connections. App separation supplies ownership/deployment boundaries, not independent compute isolation or scaling.

## Preconditions and remaining choices

Verify actual plan OS/SKU, runtime/container/Functions support, Always On, permissions and spare capacity before deployment. B1 appears in inspected platform defaults but is not proven sufficient or accepted as the final workload tier. No plan capacity/SKU changes or spending are authorised by this decision.

Network access follows ADR-026; Local/dev environment scope follows ADR-025. Production hosting is a later decision.

## Verification

Deploy through authorised app scopes and prove distinct identities/configuration, image pull permissions and compatible runtime startup. Load-test concurrent API/photo/AI work and agree extraction/capacity thresholds before increased load. Do not provision unused later-stage apps merely to demonstrate service count.
