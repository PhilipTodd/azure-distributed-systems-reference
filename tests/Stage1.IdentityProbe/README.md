# Local Stage 1 customer identity verifier

Verification tooling only, not Parameter Pilot feature implementation. Uses the approved UI registration and localhost:4200 callback; no tank, measurement, SQL or Cosmos access. Requires the recorded customer registrations and separate Local OBO certificate in CurrentUser/My. Runtime dependencies are pinned and locked.

Run `npm ci --ignore-scripts` in this folder, `dotnet restore --locked-mode`, then `dotnet run -c Release`. The server binds localhost:4200, rejects other Host headers and cross-origin verification requests, uses a per-process request nonce, limits request size and disables logging. Keep it running only during the authorised test and stop afterwards.

The browser uses MSAL Browser 5.27.0 with its supported sessionStorage cache; sign out/close the test browser session to clear authentication state. The Local certificate key is non-exportable; neither key nor tokens are exported. In identity-only mode, tokens reach only Microsoft's token service and this loopback process; evidence contains checks/IDs/thumbprints only. Authentication codes and passcodes are not evidence.

For the separately authorised Step 5 hosting test, the coordinator creates an ignored `.hosting.json` file. Refresh the page to select deployed verification mode. The loopback server then forwards customer tokens in memory only to the exact shared APIM hostname and the two PP backend hostnames, testing valid gateway calls and denied direct calls. Tracking exchanges the token using its Development vault certificate. This mode writes separate hosting evidence and preserves Step 4 identity evidence. The coordinator's bounded watcher removes the mode file and restores the temporary Azure changes. See [hosting runbook](../../docs/infrastructure/hosting-ingress-verification.md). Stop this Local process after testing.

User enters email passcodes directly at Microsoft, then selects Verify tokens and OBO. The server validates signatures against the tenant's HTTPS discovery/JWKS, own API audience, issuer/lifetime, scopes and tid + oid mapping. It tests wrong audience/issuer/tampered signature and certificate-authenticated OBO from Tracking to Aquarium.Read; wrong incoming audience and unconsented downstream Write must fail. MSAL performs client authentication and token exchange; this is not a handwritten OAuth implementation.

These results prove Local identity protocol/configuration, not product API/APIM authorisation, tank ownership, production session behaviour or Development Key Vault private-key loading. Those remain explicit implementation/hosting checks. Do not add product resources or broaden consent to make a test pass.

The UI is consented for both Read and Write. Microsoft Entra can include all previously granted scopes in a token even when a request asks only for Read; request scope is not token downscoping. The initial verifier incorrectly treated a Tracking.Read request as proof of a read-only token. Its failed result is retained. The corrected verifier checks the UI token against the approved scope set, then uses the genuinely Aquarium.Read-only OBO token against a Local HTTP write-permission probe: it must receive 403, with a consented UI write-token positive control receiving 204. That endpoint performs no data mutation and uses the same issuer/signature/audience/lifetime validation helper. This is a real permission-denial check, not a synthetic edited claim or a weakened expected result. [MSAL scope behaviour](https://learn.microsoft.com/en-us/entra/msal/javascript/browser/resources-and-scopes).
